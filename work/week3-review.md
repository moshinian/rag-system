# Week 3：工程难点、优化点与效果差异

## 结论

Week 3 需要补的已经不是新的主链路功能，而是把工程化工作沉淀成可复盘、可展示、可面试表达的材料。

这一版文档只回答 3 个问题：

1. Week 3 解决了哪些真实工程难点
2. Week 3 做了哪些可解释的优化
3. Week 3 能展示哪些前后差异

## 工程难点

### 1. 异步索引链路的一致性与重复提交控制

真实问题不是“怎么把 `process + embed` 放到线程池里”，而是：

1. 请求线程提交任务后，调用方如何知道任务是否真的被受理
2. 同一文档在已有 `QUEUED / RUNNING` 任务时，如何避免重复提交
3. 长链路跨越解析、切块、向量化多个阶段后，状态如何持续可观察

当前落地方式：

1. 通过 `indexing_task` 独立记录异步索引任务
2. 用 `QUEUED / RUNNING / SUCCEEDED / FAILED` 表示任务主状态
3. 用 `task_stage / chunk_count / embedded_chunk_count` 表示阶段进度
4. 单文档存在进行中任务时拒绝重复提交

这解决的是“异步可提交”到“异步可管理”的差异。

### 2. 长链路失败恢复与重试边界

索引任务不是单 SQL 操作，而是：

```text
读取文档 -> 解析 -> 切块 -> chunk 入库 -> embedding -> 向量写库
```

任一环节出错，都可能留下中间态。

当前难点主要有：

1. 失败后如何保留原任务轨迹
2. 手动重试和自动恢复如何避免无限循环
3. 卡住任务如何识别为“异常进行中”而不是“正常耗时中”

当前落地方式：

1. 重试和恢复都生成子任务，不覆盖原任务记录
2. 增加 `retry_count / max_retry_count / last_heartbeat_at / recovered_at`
3. 对卡住的 `QUEUED / RUNNING` 任务做定时扫描恢复
4. 增加最大重试次数边界，避免无限恢复

这解决的是“任务失败了”到“任务具备最小可恢复能力”的差异。

## 优化点

### 1. Redis 读缓存接入

Week 3 前，知识库、文档、就绪度、检索结果都只能直接打数据库或检索链路。

当前已经接入：

1. 知识库详情缓存
2. 知识库分页缓存
3. 文档详情缓存
4. 文档分页缓存
5. chunk 列表缓存
6. `qa/readiness` 缓存
7. 检索结果短 TTL 缓存

同时补齐了写路径失效：

1. 知识库启停会清相关缓存
2. 文档处理、向量化、禁用会清文档与问答相关缓存
3. 检索缓存当前采用短 TTL + 写路径整缓存失效策略

这一版优化的重点不是极致命中率，而是先把读缓存能力和一致性边界做出来。

### 2. 切块参数从固定值变成可实验、可配置

Week 3 前，切块更像“先给一个能用的默认值”。

Week 3 后已经补成：

1. `rag.chunking.*` 配置外置
2. `compact / balanced / wide` 三组参数实验
3. 长 Markdown 样本对比
4. chunk 数、平均长度、过长 chunk 分布统计

这使默认切块参数不再只是经验值，而是有实验依据的折中选择。

## 效果差异

### 1. 切块参数对比结果

同一批样本的实验结果已经表明：

1. `compact(480/60/180)` 总 chunk 数最多，为 `15`
2. `balanced(600/80/240)` 总 chunk 数为 `14`
3. `wide(720/120/300)` 总 chunk 数降到 `10`

进一步差异：

1. `compact` 更强调召回粒度，chunk 更细
2. `balanced` 在 chunk 数和单块长度之间更均衡
3. `wide` 虽然块数更少，但长 chunk 明显增多，过长片段风险更高

当前默认值继续保留 `balanced`，理由已经从“拍脑袋”变成“有实验支持的折中方案”。

### 2. Redis 缓存联调结果

`e2e-20260504` 的真实联调已经验证：

1. `GET /knowledge-bases/{kbCode}` 会写入 `rag:knowledgeBaseDetail::e2e-20260504`
2. `GET /knowledge-bases?pageNo=1&pageSize=10` 会写入 `rag:knowledgeBasePage::null:1:10`
3. `GET /qa/readiness` 会写入 `rag:qaReadiness::e2e-20260504`
4. `POST /qa/retrieve` 会写入 `rag:qaRetrieval::e2e-20260504:What did Week 3 deliver?:3`

同时已经观察到真实 TTL：

1. 知识库详情缓存为长 TTL
2. 分页缓存为中等 TTL
3. 检索缓存为短 TTL
4. `qaReadiness` 会按 `60s` 自然过期

这说明 Redis 已不再只是探针，而是已经承接真实业务读缓存。

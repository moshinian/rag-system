## 1. 目标

你的目标不是在 1 个月内“学完 AI”，而是：

**在 1 个月内做出一个可演示、可讲透、可写进简历的 RAG 项目，并据此支撑 AI 工程师面试。**

面试官最终会判断三件事：

1. 你有没有真实工程能力
2. 你有没有做过完整的 AI 应用项目
3. 你能不能把后端经验迁移到 AI 场景

所以这 1 个月的任务不是追求技术栈最全，而是产出最强的面试资产。

## 2. 当前定位

当前阶段，`rag-backend` 的定位固定为：

**项目的 Java RAG 主系统。**

它负责的事情包括：

1. 知识库、文档、chunk、问答记录和状态机。
2. 检索编排、Prompt orchestration、异步索引和失败恢复。
3. `qa/readiness`、缓存、审计、健康检查和运维语义。
4. 通过 `rag-ai-service` 调用模型能力，但不重新承接 provider 细节。

当前阶段它不负责的事情包括：

1. 直接适配外部模型供应商协议和密钥治理。
2. 前端工作台页面组织和交互体验。
3. 为了“看起来更复杂”而引入与主链路无关的重型基础设施。

这部分边界应继续保持稳定，不要把 provider 适配重新吸回 Java，也不要让业务主链路被次要技术选型打散。

## 3. 下一阶段重点

下一阶段优先继续收口这三件事：

1. 面试化资料：README、架构图、接口说明、难点总结、讲稿和简历表述。
2. 主链路稳态：继续保证文档接入、异步索引、检索、问答、恢复和健康语义不回退。
3. 工程证据：把已经成立的设计取舍、实验结果和联调事实沉淀成可复述材料，而不是只留在代码和周记里。

当前阶段的重点不是再发散功能，而是把已经做出来的系统讲清楚、证据化、可复盘。

## 4. 详细规划

## 4.1 技术路线

考虑到你的背景和时间限制，建议技术栈固定为：

1. 主语言：`Java`
2. 服务框架：`Spring Boot`
3. 主存储：`PostgreSQL`
4. 向量能力：`pgvector`
5. 缓存：`Redis`
6. 模型调用：通过 `rag-ai-service` 统一承接 OpenAI-compatible provider
7. Python 角色：除评测和实验脚本外，当前还承接独立 AI Gateway

当前阶段不建议优先引入：

1. `Elasticsearch`
2. `Milvus`
3. 复杂 Agent 框架
4. 本地大模型部署
5. 过重的多组件架构

原因很简单：

**你现在的瓶颈不是组件不够多，而是要在 1 个月内把项目做完整、讲完整。**

## 4.2 项目定位

项目建议定位为：

**企业知识库 RAG 问答系统**

项目必须覆盖的能力：

1. 文档上传
2. 文档解析
3. 文档切块
4. 向量化入库
5. 检索召回
6. 大模型回答
7. 引用来源展示
8. 文档元数据管理
9. 问答记录保存
10. 基础评测

项目不要一开始做得过重。  
你当前最重要的是做出一个完整闭环：

**上传文档 -> 建索引 -> 提问 -> 检索 -> 回答 -> 展示引用**

---

## 4.3 为什么当前优先 PostgreSQL

你这次冲刺阶段，优先 `PostgreSQL` 而不是 `Elasticsearch`，不是因为 ES 不好，而是因为：

1. `PostgreSQL` 可以统一承载主数据
   - 知识库
   - 文档元数据
   - Chunk
   - 问答记录
   - 任务状态
2. 加上 `pgvector` 就能完成基础语义检索
3. 系统组件更少，开发和排障成本更低
4. 面试时更容易讲清楚系统边界和设计取舍

你可以把 `Elasticsearch` 作为后续优化方向，但不是现在的必选项。

面试时可以这样回答：

**第一阶段我优先选择 PostgreSQL，是为了降低系统复杂度，先把主数据管理、向量检索和问答链路统一起来，快速完成端到端闭环；如果后续数据规模和全文检索要求上来，再引入 Elasticsearch 做 BM25 和混合检索。**
